### 四个硬信号

**S1 — 动笔前一次想透**（对应「低承诺入口」缺失）
首次 `draft_write` 之前的思考占全拍 **90% / 82%**（墙钟 62% / 80%）。
模型知道 draft_write 是全量替换、错了要整篇重交，因此在脑内把整篇预演完才敢动笔。

**S2 — 三连全文重交，改动极度局部**（对应 draft_edit 缺失）
f2 逐稿 diff（段落级）：

| 稿次 | 重交全文 | 实际改动 | 净变化 |
|---|---|---|---|
| v0→v1 | 809 字 | 5/21 段（337 字 = 40%） | −33 |
| v1→v2 | 798 字 | **2/21 段（95 字 = 12%）** | −11 |
| v2→v3 | 725 字 | 7/21 段（294 字 = 37%） | −73 |

为改两句话重交 798 字全文。**模型自己点破了这件事**（f2 思考 L233 原文）：

> "the tool says 逐处用 draft_edit 定点替换修正 - but I don't see a draft_edit tool in my available functions. I only have draft_write (full replacement), draft_check, world_state_update. So I'll just resubmit the full trimmed text via draft_write."

`src/draft.ts:518` 的验收报告在**推荐一个不存在的工具**。这是本次考古最直接的一击。

**S3 — 字数违规占打回 3/5，模型手工数字数**
f2 思考里逐条手算「这句能省 ~15 字」共 **7 次**（原文 `saves ~15/~15/~10/~6/~8/~8/~4`），两轮裁剪仍超（882→809→798，上限 800）。
纯机械活，且模型没有可靠的字数感——它估的和 `extractDraftBody` 口径对不上。

**S4 — 同一条规则冲突每拍重演**（**非工具问题，装配层问题**）
`<pov>「描述我的感受和想法」` vs `<user_boundary>「❌ 不能写内心想法、主观感受」`——
两块都来自 TGbreak 预设、都被 M-C 判为常驻，**语义直接打架**。
模型 f1 花 9%、f2 花 8%+18%（同一拍内纠结两次）去调和，且两拍各自重新推导一遍、结论还不完全一致。
**这不该由工具解决**——应在 M-C 拆层表里标注互斥块，或装配期给出优先级裁决。归 M-C2 补丁。

**S5 — 记账 schema 试错（并挖出现网 bug）**
f1 连续三次 `world_state_update`（activities：记账 9 项 / 1 项 / 1 项），思考 14% 用于猜 inventory 格式。
根因是 `src/state.ts:145`：

```
patch inv = [{"name":"补气丹","数量":0}]
  applied : ["inventory → []"]     ← 回报「成功」
  warnings: []                     ← 零警告
  result  : []                     ← 数据静默丢失
```

`.filter(x => typeof x === "string")` 吃掉全部非字符串元素，`applied` 仍回报成功。
模型收到「成功」却看见空数组，只能反复试。**详见 §5。**

**S6 — 流式重复上屏（M-A 遗留 UX 债，坐实）**
流出正文 vs 落树正文 = **2.9x（2216/773）/ 4.0x（3174/798）**。
且末尾还整稿重发一次：f2 末尾重发的 725 字版本**与已验收的 798 字稿不同**，未经验收、直接丢弃。

## 2. 渠道二：源码类比的关键裁决

完整 72 条设计原语见调研报告。以下只列**改变本提案结论**的几条。

### 2.1 撤销/回滚：原候选建议撤案 ⚠

记忆 `liyuan-rp-agent-plan` 把「Rollback/Undo（草稿回滚）」列为新增候选。核查结论**推翻它**：

- **Claude Code 工具层无 Undo**；能力在 harness 层的 `file-history/<uuid>/<hash>@vN` 版本快照。
- **Codex 工具层无 Undo**；曾有的 `undo`/GhostCommit 特性**已退役**（`features/src/lib.rs:838` 标 `Stage::Removed`）。回滚故事全靠 git，且系统提示**严禁**模型自行回滚（"NEVER use `git reset --hard` unless specifically requested"）。

**原语 72：撤销不是工具，是外部基础设施。模型只被允许前进式修改，回退权保留给 harness 或人。**

映射到梨园：草稿只活在单拍工作区、只有模型一个写者、且 `draft_write` 全量替换本身就是「回到任意版本」的能力。
**建议不做 draft_rollback**。若确需，代价最低的形态是 `draft_check` 报告里附一句「上一稿全绿版本仍可用」，而非新工具。

### 2.2 read-before-write 门禁：建议**不照抄**

Claude Code 的「必须先 Read 才能 Edit」是因为文件可能被外部改动。
梨园工作区是**单拍内存对象、唯一写者是模型自己**——它刚写的稿子就在自己上下文里。
强上门禁只会多一轮往返（违背提速 KPI）。**这是一处应当有意偏离的类比。**
（但 `draft_read` 工具本身仍要有——见 §3.2 的用途。）

### 2.3 定位机制：唯一性 + 模糊阶梯 + 回显

| 原语 | 出处 | RP 落地 |
|---|---|---|
| 定点定位靠唯一性（`old_string` 不唯一即报错） | Claude Edit | `resolveDraftEditText`（draft.ts:202）**已实现此语义**，直接可用 |
| 定位绝不用行号，纯内容锚定 | Codex `seek_sequence.rs` | 正文无行号概念，天然契合 |
| 匹配放宽是有序阶梯（精确→忽略尾空白→trim→Unicode 标点归一） | Codex `seek_sequence.rs` | **中文正文尤其需要**：直角引号/弯引号/全半角标点/省略号变体极易不一致 |
| 不回报宽容度是个缺陷 | Codex（该报告明确点为可改进点） | 我们**做得比 Codex 好**：命中第几级要写进 toolResult |
| 失败时回显模型自己的断言 | Codex `lib.rs:790` | old 找不到时原样退回它声称的 old，让它自己发现幻觉 |
| 先验证后提交换取原子性 | Codex `lib.rs:183` | `edits[]` **全部定位成功才落笔**，任一失败则整批不改 |
| 成功要静默（"不要 apply_patch 后重读文件验证"） | Codex `gpt_5_2_prompt.md:130` | draft_edit 返回**紧凑确认 + 复验报告**，不回吐全文 |

### 2.4 计划工具：对应 S1，但有下限约束

`update_plan` / TodoWrite = **把长任务中间状态外部化**（原语 16）。
S1（动笔前 90% 思考）正是「中间状态无处安放」的症状。
但原语 19 同时警告：**「最简单的 25% 任务不要用计划」「不要做单步计划」「不要用填充步骤凑数」**。
一拍 800 字正文很可能就落在那 25% 里 → 故列为**候选**而非必做，见 §3.4。

## 3. 工具清单提案

### 3.1 `draft_edit` —— M-B 必做（**核心，全部收益的载体**）

**理由**：S2（改动 12–40% 却重交全文；模型明说找不到这个工具）+ S1（无 edit 是「动笔前一次想透」的直接成因）+ S3（裁字数是典型定点操作）。
`draft.ts:518` 已在推荐它，`resolveDraftEditText` 已实现定位语义——**这是一件半成品，不是新建**。

**形态**（综合 §2.3 七条原语）：

```
draft_edit(edits: [{ old: string, new: string }, ...])
```

- `edits[]` **批量**，对应「多文件 patch」的 RP 版：一次报告里多处违规，一次调用改完（省往返 = 提速 KPI）
- **先验证后提交**：全部 old 定位唯一才落笔；任一失败整批不改，返回失败项
- **模糊阶梯**：精确 → 忽略首尾空白 → 中文标点归一（`""''「」『』…—－` 与半角互换）
- **命中级别回报**：非精确命中要说明「按标点归一匹配」——比 Codex 强的地方
- **失败回显**：原样退回它声称的 old + 提示用 `draft_search` 取精确原文
- **改稿即验**：与 draft_write 收稿即验同理，返回紧凑确认 + 复验报告，**不回吐全文**（原语 13）

**与现有工具的边界**：
- `draft_write` 仍是**唯一交稿入口**（首稿必须经它）；`draft_edit` 只能改**已存在的稿**，无稿时报错引导先 draft_write。写入唯一入口原语不被破坏——工作区仍只有一个 draft 对象。
- 契约指路：draft_write 描述加「局部修改用 draft_edit，不要重交全文」；system「写侧三件」→ 五件。

**实现难度：中低**。`resolveDraftEditText` 现成；执行归 `workspace.ts::runWriteTool`；引擎分发零改动（READ_TOOLS 之外全走写侧）。新增：模糊阶梯 + 批量原子性 + schema。落点 workspace.ts / tools.ts / draft.ts。

---

### 3.2 `draft_read` —— M-B 必做（**轻量，但别按 Claude 的理由做**）

**理由**：不是 read-before-write 门禁（§2.2 已论证应偏离），而是三个实际用途——
① 多轮改稿后模型对「现稿到底长什么样」失去准头（f2 三稿后已出现字数误判）；
② `draft_edit` 失败后取精确原文的兜底；
③ 触发压缩/长循环后现稿可能已不在上下文近端。

**形态**：返回现稿全文 + 稿次 + **`extractDraftBody` 口径字数**（关键：与验收器同口径，直接消解 S3 的估算误差）。

**与现有工具的边界**：与 `draft_check` 分工——check 回答「哪里不合格」，read 回答「现在写的是什么」。

**实现难度：低**。工作区上包一层纯函数。

---

### 3.3 `draft_search` —— M-B 必做（**edit 的配套**）

**理由**：S2 的配套——`draft_edit` 要求 old 精确唯一，模型需要一件工具去**取**那个唯一片段。Claude Code 的 Grep→Edit 配对就是这个关系。

**形态**：命中处 ±24 字上下文引用，≤8 处；命中多处时**明确提示「old 需扩大到唯一」**（把唯一性约束前移到检索阶段，减少 edit 失败往返）。

**与现有工具的边界**：`memory_search` 查**历史**剧情库（跨拍），`draft_search` 查**当前稿**（拍内）。两者语义不重叠，但**名字容易混**——描述里要写死「本拍现稿」。

**实现难度：低**。

---

### 3.4 `turn_plan` —— **候选，建议本轮不做**

**理由**：S1（动笔前思考 90%/82%）是最大的单项，计划工具是它的正面解（原语 16）。

**但建议缓做，三条理由**：
1. 原语 19 明确警告「最简单的 25% 任务不用计划」——一拍 800 字正文很可能正在此列，硬上会变成「填充步骤凑数」，**思考量不降反升**。
2. **draft_edit 可能已经顺手解决它**：S1 的成因是「全量替换 → 错了代价高 → 先想透」。edit 把改错的代价降下来后，「低承诺入口」自然成立（模型可以先写个开头再补）。**应先用 M-B 实弹验证这条因果，再决定要不要 turn_plan。**
3. 它与预设自带的 `draft_notes`（H 类脑内 harness，M-C 刚让它退场）形态高度重合——重新引入需要谨慎，别把刚拆掉的东西换个名字装回来。

**建议**：M-B 实弹后看「首次 draft_write 前思考占比」是否从 90% 降下来。**若仍 >70%，再单独立项 turn_plan。** 这条写进 M-B 验收指标。

### 3.5 `lore_list` / 角色档案列举（Glob 类比）—— 候选，低优先

**理由**：Glob 的 RP 对应物。但渠道一**没有产生对应信号**——两拍检索 5 次全部命中或合理未命中，模型没有表现出「不知道有哪些条目可查」的困扰（世界书条目名已在【相关设定】里可见）。

**判断**：**证据不足，不做**。列在此处仅为闭合类比表。若将来出现「反复检索同一无效关键词」的信号再启动。

## 4. 非工具改造（同属 M-B 范围）

### 4.1 `draft_check` 报告精确化 —— 建议做，性价比最高

S3 的真正解法不是新工具，是**让报告替模型算账**（原语 9/10：失败反馈即结构化报告、写成第二人称修复指令）。
现状：`正文 842 字，超过预设上限 800——需删减。`
建议：`正文 842 字，超上限 42 字。用 draft_edit 定点删减约 42 字（当前每段均长 40 字，约 1 段）。`

**理由**：模型手算 7 次「saves ~15」全部是在做这件事，且算不准。代码算是 O(1)。
**难度：极低**（draft.ts:465 一行文案 + 差值）。**预计直接吃掉 S3 的大部分（f1 12% / f2 9% 思考）。**

### 4.2 wire 替换帧 —— M-A 遗留 UX 债

S6：重复上屏 2.9x/4.0x，末尾还重发一版未经验收的稿。
需要 `assistant_replace` 类帧（wire.ts:257 现只有 `assistant_delta`）。
`draft_edit` 落地后这件事**更急**——定点改动若仍走全量重发，屏上会更乱。
**难度：中**（涉及 server/wire.ts + 前端渲染，跨模块）。

### 4.3 展示块渲染管道（D-C3 欠账）

w2g 选择框 / catsay / 摘要以账本渲染补回。
渠道二给了它一个**设计依据**（原语 54）：`request_user_input` 强制 2-3 个互斥选项、推荐项排首位、「Other」由客户端追加、**子代理不得提问**。
选择框不是「格式栈残渣」，是**把主动权交还用户**的结构化形态——与 TGbreak `user_boundary`「需要 user 做重大决定时停下来」同构。
**建议**：作为 M-B 后半独立落地，可与工具部分分开。

## 5. 实弹挖出的现网 bug（建议顺手修，独立于 M-B）

`src/state.ts:145` `inventory` / `plot_threads` 分支：

```ts
next[key] = value.filter((x): x is string => typeof x === "string");
applied.push(`${key} → [${next[key].join("、")}]`);
```

传入对象数组时全部元素被静默丢弃，`warnings` 为空，`applied` 仍回报成功（实测见 S5）。

**建议修法**（对应原语 11「回显模型自己的断言」+ 15「先验证后提交」）：
过滤掉的元素要进 `warnings`，并回显被丢的原值 + 说明期望形态（字符串数组，如 `["补气丹（已服用）"]`）。

**这是数据静默丢失，不是工具缺失**——建议独立于 M-B 修，也可作为 M-B 第一个 commit 的搭车项。**请用户拍板归属。**

### 8.4 关于「表格/plan」的悬而未决

### 8.5 方法论教训（重要）

1. **实弹必须钉死开场白**：`/greeting` 无参会推进并**持久化** greetingIndex，
   首轮 M-B 实弹因此漂到另一张开场白，数据不可比且被误报为 −89%/−95%
   （真实同卡对照是 −49%~−65%）。脚本一律用 `/greeting <固定序号>`。
2. **n=2 不足以下结论**：两拍数据让「工具有没有用」反复摇摆；跑满 4 拍才看出
   「首拍 vs 非首拍」才是主轴（3.3 倍差）。
3. **比例要看分母**：同一现象在 7209 与 30557 两个分母下，占比可以差 4 倍。
