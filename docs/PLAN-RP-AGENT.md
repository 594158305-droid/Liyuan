# PLAN-RP-AGENT：把扮演当成代码来生成（tools 层 + harness 层设计契约）

> 2026-08-03 定稿。前置：用户定案「死磕思考问题」；46KB 思考文件逐行实证（本地留档）；上轮 harness 重建（PLAN-RP-HARNESS.md）M0–M4 已实弹验证但
> M4.5 提速负收益、M5 未做。本文档是「RP agent 化」的完整设计契约——tools 层（写作工具栈）+
> harness 层（预设拆三层），两层合起来回答一个问题：**为什么梨园不是 RP agent，以及怎么把它变成**。

## 0. 根因（2026-08-03 用户定案，逐条实锤）

三个判断全部成立，且最后一个才是根因：

1. **预设污染 harness —— 真**：67 启用块 / 49173 字全量常驻 system+postHistory（`_preset-taxonomy.md`
   实测）。模型分不清哪些是会被代码验收的契约、哪些只是风格参考，只能全部脑内自验。
2. **冲突引发循环思考 —— 真**：46KB 思考里 30 行纠结「摘要 vs UpdateVariable 谁最末尾」、30 行纠结
   「pov 写感受 vs boundary 禁写内心」、8 行纠结 JSON patch 用 replace 还是 insert。每拍重演一遍。
3. **工具缺失是主因 —— 实锤**：真实 server 走 `StageEngine`（server/main.ts:1976），其工具清单
   （`src/stage/tools.ts` stageTools）**只有 3 个只读工具**：lorebook_search / memory_search /
   world_state_get。**draft_write/draft_edit 在 roleplay.ts 与 stage 两套路径都零注册**——模型
   根本拿不到稿纸工具。8/02 稿纸实弹通过是旧 roleplay.ts 路径，8/03 harness 重建把生成路径换到
   StageEngine 时工具组没迁移，RP agent 化的「写侧」整个丢了，只剩「读侧」。

**更深的根因（用户点破）**：这不是 RP agent。coding agent 的全部循环围绕**工件**（代码文件）转：
外部化、可读写、可验证、可迭代。梨园的循环围绕**消息流**转：正文只是 stream 一轮的副产物，生成完
落树即成历史，模型视角里它不可改、不可验、没有测试兜底 → 所有打磨只能在 thinking 里脑内排练。
**剧情文字没有获得「代码」的地位，因此也没有代码的待遇。**

「思考问题」的完整成因链：正文不是工件 → 没有外部工具承接写作/修订/验收 → 模型只能脑内自建
工件循环（排练正文 123 次 + 脑内账本 patch 32 次 + 字数自检 17 次 + 格式核对 34 次）→ 46KB 思考。

## 1. 北极星：用户最终要看到的东西

不再是一段几万字的思维链，而是：

```
思考(读题+决定) → 调用工具 → 看结果 → 再思考 → 再调用工具 → …… → 定稿
```

和 coding agent 一样。思考只留「读题 15% + 决定 10%」，其余 75%（排练/验算/纠结）的**工作**全部
由外部承接——**拆迁而非抑制**（延续 PLAN-RP-HARNESS §0.1 结论，断粮已证伪不再碰）。

## 2. tools 层：为扮演准备的工具栈

### 2.1 现状核对

真实引擎模型只有 3 个只读工具。连写账本的工具都没有 → 模型只能脑内"演"UpdateVariable，再塞进
正文当格式标记让外部解析。**这不是 agent 调用工具，是交格式约定作业。**

### 2.2 工具栈设计（类比 coding agent）

| coding agent | RP 对应 | 承接的脑内工作 |
|---|---|---|
| `read` | draft_read 读当前稿 | 回读确认 |
| `write` | draft_write 写稿（**唯一交稿入口**） | 排练正文 123 次 → 0 |
| `edit` | draft_edit 定点补丁（edits[] 数组） | 重写 v2/v3 → 定点改 |
| `grep` | draft_search 定位文字（配合 edit） | 找到要改的那句话 |
| `test`/lint | draft_check 验收报告（代码判：字数/禁词/格式区块/JSON patch/重复） | 字数自检 17 次 + 格式核对 34 次 + 禁词验算 → 全交代码 |
| 账本工具 | world_state_update 写账本（**丢失，挂回**） | 脑内 patch 32 次 → 定稿后一次调用 |
| bash/执行 | 引擎内部：补丁套用 + 复验 | 脑内修订演练 → 看真实报告 |

### 2.3 结构变化（关键）

1. **工具循环开放式**：不是 M3 的"封顶 MAX_LOOKUPS=3 次检索"，而是"思考 → 工具 → 看结果 →
   再思考 → 再工具"直到 draft_check 全绿，允许很多轮（同 coding agent）。
2. **draft_write 是唯一交稿入口**：不用工具就交不了稿 → 脑内排练物理上无处安放。
3. **精修从"harness 后台偷做"改成"模型可见的迭代回合"**：8/02 的 #revise 是 harness 用旁路
   （#sideText, reasoning:off）在模型不知情时偷做的后处理——模型不知道自己有稿子可以改。必须
   让它像 coding agent 看测试报错一样看 draft_check 报告。
4. **验收器是代码不是模型**：预设纪律类约束全部转成 draft_check 规则，不进思考。

## 3. harness 层：预设拆三层（污染解法）

### 3.1 关键定位：预设 = skill

预设中除破限外的部分，本质是**教模型如何写作**——方法论、流程、写法要点。这和 coding agent 的
SKILL.md 是同一种东西：一份"教 agent 干某件事"的领域指导文档。而它现在的形态恰好与 skill 相反：

| | skill | 预设现状 |
|---|---|---|
| 加载 | 按需，匹配任务才加载 | 67 块全量常驻 |
| 边界 | 有明确边界，agent 知道"我在按它执行" | 无边界，模型不知道哪些是契约哪些是参考 |
| 副作用 | 不在上下文即不占注意力 | 全部变验算目标 |

**污染 = 把 skill 当 system prompt 用了。**

### 3.2 为什么"加一个提示词层"不够

提示词层只能解决**文风**（在场即用、读了就照做）。但占思考的大头是**方法论**（draft_notes 模板、
写作流程、检查清单）——这类内容的价值只在"执行写作动作的瞬间"，常驻上下文不产生收益，只产生
"这是不是要我满足？"的验算。方法类必须**按需加载**，不是换个位置常驻。

### 3.3 三层结构

| 层 | 内容 | 形态 |
|---|---|---|
| 提示词层 | 文风特征摘要（几百字：话痨/阴冷/用词习惯） | 常驻 system，在场即用，不引发验算 |
| skill 层 | 写作方法论（draft_notes 模板/流程/检查清单） | **按需加载**——写作阶段模型像 coding agent 读 SKILL.md 一样读一次，用完即走 |
| 代码层 | 纪律（禁词/字数/格式区块/破限/JSON patch） | **根本不进模型**，转 draft_check 验收规则 + 门禁 |

模型每拍的验算目标从 67 块降为 0 块。破限归代码层——它是"不做什么"的清单，本质是验收规则。

### 3.4 现有资产直接接上

`src/preset-classify.ts` 性质分类器（文风/纪律/结构/噪声四类）就是拆层的分类基础。装配动作：

1. 文风类 → 压缩成摘要进 system
2. 方法论类 → 存成"写作 skill"，写作阶段注入（一个加载动作，不是常驻）
3. 纪律类 → 转成 draft_check 规则（代码判）
4. 噪声类 → 直接丢

结果：49173 字 → system 里只剩几百字文风摘要 + 写作时读一次方法论 + 纪律全代码。

## 4. 两层合流后的完整一拍的形态

```
装配（system=harness 规则+文风摘要；纪律已代码化，不在上下文）
  → 模型思考（只读题+决定）
  → draft_write 写初稿（方法论 skill 已加载）
  → draft_check 验收（代码判：字数/禁词/格式/JSON）→ 报告喂回
  → 模型看报告 → draft_edit 定点改（可多轮）
  → 复验全绿 → world_state_update 记账（一次）
  → 场记/压缩照旧
```

思考量预期：high 档 3k–14k 字 → 仅剩读题+决定（几百字级别）；墙钟随之下降（排练是慢因 A 大头）。

## 5. 验收标准（用户定）

1. 用户看到的循环形态：**思考 → 调用工具 → 思考 → 调用工具**，而不是长思维链。
2. 15 层实弹（TGbreak 预设 + 模拟修仙卡，每层 roll 两次）中：每层思考量显著下降、draft_write/
   draft_edit/draft_check 调用可见、正文质量不倒退（双 KPI：演得好 + 跑得快）。
3. 预设污染可视化：用户能在装配层看到每块预设去了哪一层。
