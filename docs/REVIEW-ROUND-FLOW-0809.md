## 1. 输出形式定案的最终落地形态

```
第 1 轮   【第 1 步·规划】读题 → 探索 → beat_plan 列路标 + 字数分配（不落正文）
每段循环  【演段回看】回看 → 思考戏与文笔 → draft_append 一段
          └ 违规 →【修复】只能 draft_edit（append/done/seal 全拦）→ resync 原位替换上屏
路标耗尽  字数不够 →【续写】承接世界书下文；涉及用户行动 → ask
收笔前    【收笔评估】① 下文涉及用户行动？→ 先 ask ② 停点？③ draft_seal
封笔后    【谢幕】记账 → 状态栏（= 本拍结束标志，必须最后；程序化保底）
落树      稿段分段原位 + 尾巴独立末段（重放形态 = 流式形态）
```

硬保障（不靠模型自觉）：
- 同轮连发门禁（一轮只演一段）、零思考门禁（append 前必须有思考）、
  未修违规门禁（append/done/seal 全拦，只放行修复与只读）
- 程序化谢幕：停手时稿/text 通道缺状态栏标签 → 必开一轮点名催告（替代 hasTailIntent 猜词）
- M-E 兜底封笔、直出代收、催稿、空手认栽（原有，未动）

## 3. 待用户拍板（未动）

1. **状态栏提醒的层数**：现有四层（每拍注入块 / seal 回执 / 收笔评估卡④ / 程序化谢幕）。
   在「时有时无」的伤口上宁多勿少，但对提示词膨胀敏感的话可以砍注入块层（程序化谢幕
   是真正的保底）。
2. **P6 draft_write 门禁扩判据**（PLAN §10 遗留）：现只按 lookups>0 拦；纯情感戏/纯场景戏
   （不查库）仍可一次交完。提案：查过库 **或** 计划≥2 条即拦。
3. **ask 落树留痕**（PLAN §10 遗留）：台上 ask 走 live 选择卡，重放不还原已决卡
   （wire.ts choiceOfToolResult 只认旧 ask_director 名）。
4. **sov 主权检查的第一人称盲区**：`checkSovereignty` 主语集只有 `userName|你`——
   用户第一人称视角卡（正文以「我」= 用户自称）的代言完全漏检。加「我」需要卡级
   视角判定（哪些卡「我」= 用户），误伤面大，需要设计。

## 4. 遗留观察项（无需动作）

- 修复卡在 sealed 语境下「验收过了再构思下一段」措辞略不合（修完即转谢幕卡，影响一轮）。
- 演段回看卡的思考量稳定性：8/09 实弹各段思考 100–1500 字（对比 8/08 的 30 字已改善），
  但 n 还小，按实弹纪律继续观察。
- `stream:clear` 只在传统 agent 路径（session.subscribe）触发，StageEngine 不经过——
  前端 dropTrailingText 的稿段保护属防御性修正。
- 连勾多步（done+done 连发）不拦：勾步不产正文，危害小。
