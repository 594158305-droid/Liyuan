# 自定义表格 LLM 填表遵从度优化（TavernDB 导入模板）

## 背景与根因

2026-08-10 评价结论：当前会话（019fe720-…）19 张 auto 表的 description 是 SillyTavern 系统原样移植的 SQL 规则，与本引擎 `table_*` 工具（JSON match/changes 语义）错位严重，导致遵从度低（4 张空表、纪要编码重复、全局地点违规等）。

三个根因：
1. **规则载体错位**：模板 `note` + 4 个 SQL 触发器（initNode/insertNode/updateNode/deleteNode）原样拼进表 description——SQL 语法、`row_id` 幽灵列、英文表名/列名、`db.*` 查询语法、残句「禁止。」全量残留，场记照抄即错。
2. **列级说明丢失**：模板列都带 description（DDL 注释提取的列说明），但物化时 `dedupeColumns`（src/state.ts:421）只保留 name/type，列说明被丢弃——「白描技法是什么」「字数多少」这类列级澄清无载体。
3. **规则自相矛盾**：备忘录 YYYY-MM-DD vs 自定义历法、恋爱日记 writer 准入 vs 示例用「主角」、全局数据表「严禁 - 层级」vs 示例自带 `-`；「固定 5 行 + 每轮全量重写」的 INSERT OR REPLACE 语义本引擎无支撑。

机制确认：场记每轮把整个账本 JSON（含表/列 description）注入【当前账本】（src/scribe.ts:63-64），description 是场记填表的最高优先级规则；列 description 若落地也会随 JSON 进场记上下文，但不进剧情上下文（assemble.ts 只 formatState 行数据）。

### 阶段 A：模板重写（`.liyuan-templates/TavernDB 导入.json`，纯文案，工作量主体）

**A1. note 重写规范（19 表逐表重写，统一结构）**：
- 每表按固定骨架：`表定位`（记什么/不记什么）→ `列定义`（真实中文列名 + 含义 + 字数区间 + 格式示例）→ `维护规则`（本引擎工具示例）→ `跨表引用`（引用表名+列名+一致判定）→ `红线`（禁止/必须，无歧义、有宾语）。
- **字数限制明确化**：所有列给出字符区间（如「≤30字」「80~120字」「200~400字」），注明按汉字计；「未知」列豁免字数下限（呼应全局填表纪律第 1 条）。
- **术语就地定义**：白描技法、身体基线、性格偏移、禁止臆测、门控校验、引用 vs 搬运（关联 = 只填引用键，不搬内容）等，在首次出现的表内给出定义 + 正反例。
- **跨表引用写全**：如「角色名称须与恋爱对象表（列：姓名）一致」——引用表名+列名+判定规则写完整，不留「XX表」这种半引用。
- **列定义三型标注（每列必选其一，2026-08-10 用户反馈）**：
  - 【静态快照列】服饰/外貌/生理状态等：只写款式/颜色/材质/有无等客观现状，如「黑色无领带西装」；没穿直接写「无」。**禁止过渡描写**——禁止「衣服被怎么怎么样然后怎么怎么样」的动作/过程/结果叙事（实证：在场角色表服饰列被写成性爱过程小作文）。
  - 【结论列】态度/关系/情绪/称呼等：一句话结论（如「暧昧对象」），允许枚举取值。**禁止叙事化关联**——禁止把「对主角态度」写成一段像故事一样的展开（实证：态度列写成「经历了XX后她…」的小作文）。
  - 【事件列】过往经历/纪要/日记等：只在事件发生时记。**禁止占位符**——禁止「（前略）（省略）」等偷懒占位（实证：重要角色表「过往经历」出现「（前略）」）；细节由正文与 memory_search 承担，本列只留结论性要点。

**A2. 四触发器清空**：内容并入 note 后，`initNode/insertNode/updateNode/deleteNode` 字段删除（物化合并串不再出现 SQL；auto 标记独立保留，不受影响）。

**A3. SQL 清除（14 表）**：
- 所有 `INSERT INTO ... VALUES` → `table_insert(table:"表名", row:{...})` 示例；`UPDATE ... SET ... WHERE` → `table_update(table, match:{...}, changes:{...})`；`DELETE FROM ... WHERE` → `table_delete(table, match:{...})`。
- 删除：`row_id` 及 `COALESCE(MAX(row_id),0)+1`、SQL 英文表名（romance_targets 等）、`insertNode/updateNode/deleteNode` 字眼、`{[db.xxx.where(...)]}`、`<if cond=...>`、`{[db.calc(...)]}`、`$v:`、无宾语残句。

**A4. 矛盾修复清单（逐表）**：
- 备忘录：时间格式以自定义历法为准，删「严格 YYYY-MM-DD」硬要求；「已完成/已取消即删除该行」补上「已解决」等同义状态。
- 恋爱日记表：删 SQL 示例里 writer=「主角」的违规示例；准入规则保留。
- 全局数据表：「严禁 - 连接层级」补定义（只能填地图点表的地点名称；若地点未登记先补登记行）。
- 纪要表：补「编码索引唯一，新编码递增不跳号」规则。
- 主角信息表：年龄列改为纯年龄（如「22岁」），状态备注移入近况；NSFW 度量描述禁令保留（「九寸半」等改写为写实白描），补技能联动例外条款。

**A7. 增量字段分档（2026-08-10 用户裁决，先确认后实施）**：
- 依据：正文压缩时归档进 narrative 向量库，memory_search 可语义召回（src/tools/memory.ts）；「过往经历」的「识别关键项→拼接→压缩」增量规则已实测诱发「（前略）」偷懒占位。
- 【事件流水类】砍掉增量拼接：过往经历 = 「出场前背景（一次性写入）+ 里程碑列表（一句话一条，仅重大节点）」；事件细节不再进表，交给正文 + memory_search + 纪要表。删除「未达 600 字时末尾追加、超 600 字压缩至 200 字」等拼接规则。
- 【当前事实快照类】覆盖式维护：在场角色/即时生理/全局数据/服饰类列每轮直接重写本行（update match 姓名，整体替换变化列），不做增量。
- 【纯计数类】保留：调教值/性爱次数/资金/技能冷却，规则维持「+1/上限/覆盖」的简单语义。
- 纪要表保留「每轮一条」的轮次日志语义（触发时机明确、结构化），但删除行内过度约束。

**A5. 检定建议表（零源码改动方案）**：规则改写为本引擎可执行操作序列：「每轮维护 = 先 `table_delete(table:"检定建议表", match:{})` 清空全部行，再按序 `table_insert` 5 次写入 row_id 语义由插入顺序替代」——固定 5 行、禁止新增 1~5 以外行、展示文本/检定难度非空等约束保留。

**A6. 列 description 重写（19 表 × 全部列）**：每列「含义；字数区间；格式示例」，术语就地展开（在场角色表 6 部位列补「白描技法」定义：只写客观可见的穿着状态——材质/颜色/贴合/污渍/变形，每部位 ≥35 字，禁止概括词「穿着衣服」、禁止写与穿着无关的身体描写）。

## 风险与边界

- 覆写只动 description 字段，不碰 rows/columns，随世界线/回档一致回退，安全。
- 物化覆写会覆盖会话内对表说明的手动修改——模板为真值源，warning 明示。
- 模板是本地文件；若再次用 TavernDB 原文件导入会覆盖本次重写——保留原文件备份。
- 列 description 只进场记【当前账本】（旁侧模型），不进剧情上下文；19 表 ≈100+ 列 × 30~60 字 ≈ 6~8KB/轮，token 增量可控。
